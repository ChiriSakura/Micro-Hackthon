# 冻结运行后发现的诊断问题

当前 17879193 使用 source.tar.gz 中的 v3 冻结代码；下述后续代码改进仅在工作区，不修改正在执行的实验，不计为该次运行收益。

SelectionUnit 的诊断 Agent 曾把 `module case=0 step=11` 当成10拍延迟，并猜测 Seq.iterate 产生 N-2 个寄存器。实际 step 是从0开始的测试步骤索引，包含 reset，不是延迟。

工作区新增确定性时钟证据：从冻结 steps 的 cycles/reset/valid 计算每次输入接收边沿、当前采样边沿、契约输出边沿；同时携带实际捕获的数据，避免把空拍的零输入错当成原事务。例：reset在第1沿，输入在第2沿接收，step11在第12沿采样，经历11沿（包含接收沿）；12拍契约应在第13沿出结果。

Seq.iterate(seed,N)(next).last 调用 next N-1次。这个事实不应被测试索引的偏移解释推翻。提示词补充计数规则，参考源码/测试判定仍不改动。

新增测试覆盖孤立事务、reset、保持valid跨多个边沿、多拍step和原输入追溯；连同原行为测试共21项通过，见 timing_diagnostic_tests.xml。它们是控制逻辑测试，不是DynaX硬件通过证据。

工作区恢复任务提示也消除了继承自v1的措辞冲突：允许从只读库选择历史组件，但不注入旧完整系统计划或旧顶层RTL。正在运行的冻结任务保持原样；实际使用的任务文本见run/task.json及source.tar.gz。
